# Cohousing V13 回顾：这套 Harness 为什么这样设计

本页是案例复盘，不是新项目模板。它记录《中国共居叙事研究》从资料积累到 V13 双语分册交付时暴露的结构性问题。

## 1. 最终形成的真实结构

```text
source-corpus/
  raw HTML / oral history / 706 self-narratives / indices / derived
harness/
  corpus-ingest / research-tracks / docs / v13
harness/v13/
  baseline-input / coverage / research / appendices / prewriting
  scripts / build / audit
current-v13/
  complete bilingual research share package
  project-partner reader package
  validated ZIP files
```

研究原件、构建 Harness 和对外成品分开以后，删除旧稿才不会误删证据或可复现输入。

## 2. 证据轨的成熟形态

V13 最终保留了：

- 原始网页、口述史和组织自述的分层语料库。
- 覆盖 31 个省级地区的最低检索矩阵与未命中记录。
- 来源登记、项目目录、706 节点谱系、法规目录和历史事件年表。
- `verified_active / verified_historical / lead_only` 等受控状态。
- unknown、移除日志、网站查找状态和跨表映射。

关键经验：目录的数量是“在既定语料和检索式下形成的公开记录”，不是全国真实总量。项目目录与节点谱系存在重叠，不能相加。

## 3. 预写作不是摘要

预写作按八个维度展开：时间、话语、物与空间、情感、组织与金钱、背景上下文、品味、数字与数据。它的价值不是生成八份结论，而是提前发现：

- 同一数字的口径冲突。
- 某个项目只有名称，没有实际房间证据。
- 组织自述占据了话语中心，退出者和照护者缺席。
- 图片虽多，但重点案例缺少能显示真实公共生活的画面。
- 文章宏观尺度过大，缺少账本、钥匙、洗碗机等落点。

## 4. 最大结构失败：新 outline 没有真正进入正文

早期版本完成了审稿和新 outline，却主要增加标题与子标题，旧段落顺序没有真正重组。资料继续增加，连接性反而变差。

修复方式：

- 冻结旧稿为 baseline。
- 写“结构重写协议”，明确哪些章节必须发生什么移动。
- 建立内容守恒矩阵，保证事实、图片、来源不静默消失。
- 每章使用论点—证据—机制—边界—转场卡。
- 审计相同段落和同序比例，区别真实重写与机械同义替换。

这成为本 skill 最重要的护栏。

## 5. 事实多不等于连接强

文章曾经依次加入土楼、单位分房、文学影视、下岗、房地产、蛋壳、706、疫情、数字游民、OPC、人才公寓和智库观点。每一项单独都有价值，但按发现顺序累加会变成展柜。

后来的解决方案是用固定治理尺重组案例：房屋控制、进入资格、共享对象、公共劳动和安全退出。案例因机制出现，不因“我们找到了它”出现。

## 6. 来源边界需要全文扫描

《陆犯焉识》段落一度出现“靠行政力量拿回整栋房子”一类超出文本的句子。单点修正不够，因为同一种过度推断可能散布在全文。

修复方式：

- 先核原文能证明什么。
- 搜索同义断言和相同因果句式。
- 在 claim register 中把小说、口述、项目自述、政策原文分层。
- 事实审计后再做风格迁移，防止文学化再次放大确定性。

## 7. 命名、数量和现状是高风险字段

“五百盒子”被纠正为“四百盒子”；项目官网不存在时需要公开提及证据；停更不能直接写成关闭；一个品牌的管理规模不能写成单一社区实际入住。

因此母表需要稳定 ID、原名、别名、物理地点、状态、最近公开痕迹、链接类型、规模单位和 scope。

## 8. 人物附录的隐私成本高于研究收益

具名人物目录一度扩展到数十人，但项目方、住客、普通员工和照片人物的结构化汇总会制造新的隐私风险。最终人物目录永久移除；公开署名作者和公共发言者只在正文必要位置出现。

因此新项目默认不建人物附录，除非用户明确目的、公共性和合法边界。

## 9. 图片必须参与论证

用户反复要求补图，不只是为了美观：

- 土楼外景需要内景，才能理解共同屋顶下的日常结构。
- 706 的空房或长桌不如聚餐和公共劳动更能显示共同生活。
- CYC、NCC 等组织需要集体场景而非抽象 logo。
- 历史转折需要报纸、住房改革文件和工人新村的物质图像。

最终图片登记不仅保存来源和 caption，也记录图像承担什么论证任务。

## 10. 附录差点吞掉正文

完整项目目录、节点谱系、法规和年表进入同一正文后，附录长度超过叙事本身。删除研究数据会损害可复核性，但让普通读者承担数据库长度也不合理。

最终分为：

- 正文卷。
- 紧凑附录卷，每项只保留地点、介绍、最近痕迹和链接等少量字段。
- 完整 CSV 母表。
- 完整研究分享包。
- 只含说明、正文、附录和图片的项目方阅读包。

这说明“研究完整性”和“读者负担”应由不同产品承担。

## 11. 双语和格式必须在事实锁定之后

中文结构未稳定时提前翻译，会把每次事实修订复制成两份债务。最终顺序是：中文母稿结构审计 → 事实与脚注锁定 → 声口对齐 → 英文翻译 → 双语结构／图片／注释序列检查 → HTML／Word 构建。

Word 不能只生成文件名。四册都经过完整渲染、页面数量核对、联系表人工复核和无障碍检查。

## 12. 内部话语不能泄漏到公共稿

“公开发布前需补摄影授权”“靠行政力量拿回整栋房子仍会超出文本”等生产备注曾混入正文。前者属于内部工作流，后者是审稿意见而非读者叙事。

公共稿发布前必须扫描：授权待办、审稿命令、模型说明、旧版本号、本地路径和 TODO。真正的证据边界要改写成读者能理解的叙述，而不是把编辑命令原样留下。

## 13. 版本清理也是研究工作

V6、V9、V10、错误 V12 等残留曾让“当前版本”难以识别。最终只保留：当前 V13、source-corpus 和 Harness；旧稿通过精确清单可恢复地移入废纸篓。

删除前要证明目标；删除后要验证包内链接、README、ZIP 和哈希。版本管理不是美化目录，而是防止读者和下一位研究者进入错误事实状态。

## 14. 可迁移的完成定义

这次项目真正完成，不是因为正文看起来长，而是因为：

- 研究表、正文和读者附录各自承担正确任务。
- 新 outline 被真实实施。
- 事实、脚注、逻辑、声口、图片和双语依次通过审计。
- HTML、Word、ZIP 实际打开和渲染。
- 项目方无需理解研究 Harness 也能开始阅读。
- 下一次研究仍能从原件、登记表和脚本复现当前版本。
