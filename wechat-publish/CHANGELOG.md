## 2026-05-07（v8.4 迭代）

### 改动：从 2050 回顾文 rewrite-v8.4 的出版过程中沉淀的改进

- **SKILL.md**：新增以下章节
  - 「MD 文章结构灵活性」— 文档化非标准结构的处理原则（裸数字分节、歌词引用块、脚注等）
  - 「Step 4a: 图片路径多源搜索」— Obsidian vault 多目录搜索策略（images/ → media/ → 材料库/）
  - 「Step 4b: 图片尺寸与质量」— WeChat 兼容的推荐值（800px 最大宽度，JPEG quality 75）
  - 「Step 4c: Base64 缓存」— 避免重复编码的缓存策略
  - 「Step 4d: Caption 检测启发式」— lookahead 跳过空白行 + 排除规则 + 第一句拆分
  - 「Step 6: Pre-flight 校验清单」— 7 项必做检查（图片数量、base64 有效性、section 平衡、文件大小等）
  - 「复杂文章的多 Agent 工作流」— 3 个 Agent 的分工方案（脚本/图片验证/质量检查）
  - 「已知局限」— 记录 5 个已知场景及其缓解措施

- **template-spec.md**：新增样式
  - 歌词引用块（诗句斜体 + 灰色署名）
  - 卷首语/题记（斜体引用，无边框）
  - 脚注/参考资料区块（`<sup>` 正文引用 + 文末绿色编号列表）
  - Caption 拆分规则（第一句话作 caption，余段作正文）

### 原因
- 参考实现 `md_to_wechat.py` 假设所有文章都用 `### N · 标题` 结构，但实际文章差异很大
- 图片在 Obsidian vault 中分散于多个目录，单一搜索路径频繁漏图
- Caption 检测在「有空白行」「多句段落」等场景下出错
- 缺少系统化的输出质量校验，bug 到用户端才发现
- 36 张图 × 30s 编码时间，每次修 bug 都要重跑全量

### 效果
- 新文章适配：从「每次重写解析器」升级为「先分析结构 → 定制解析 → 多 Agent 并行验证」
- 图片处理：800px + quality 75 使单图 < 100KB，总 HTML 控制在 5MB 以内（原 8.1MB）
- Caption 准确率：通过 lookahead + 排除规则 + 拆分，覆盖了空白行和长段落场景
- 质量保证：Pre-flight 7 项检查在交付给用户前拦截了脚注缺失、caption 错位等问题

## 已知局限

| 场景 | 局限 | 缓解措施 |
|------|------|---------|
| 非标准 MD 结构 | 每篇文章需定制解析器 | 先通读结构 → 再写脚本 |
| 图片 caption 歧义 | 无法完美区分 caption vs 段落 | 手动 override + 排除规则 |
| 微信粘贴上限 | 总 HTML > 10MB 可能粘贴失败 | 控制图片 ≤800px, quality ≤75 |
| Base64 编码慢 | 36 张图需 30s+ | 缓存到 `_cache/` 目录 |
| 微信渲染差异 | 部分图片在编辑器中不显示 | 降低图片尺寸后再试 |
| 标准 MD 语法 (`### N ·`) | 仅覆盖一种章节模式 | SKILL.md 新增「MD 文章结构灵活性」 |
